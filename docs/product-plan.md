# TechGraph 제품 기획 초안

## 1. 한 줄 설명

TechGraph는 과학기술의 진보 상황을 증거 기반으로 추적하고, 커뮤니티가 논문, 기업 발표, 특허, 제품 출시, 실험 결과 등을 검토해 기술이 실제로 어디까지 왔는지 보여주는 서비스다.

## 2. 만들고 싶은 문제 해결

과학기술 정보는 빠르게 나오지만, 사용자가 보기에는 다음 문제가 있다.

- 논문, 기업 블로그, 뉴스, 특허, 제품 발표가 여러 곳에 흩어져 있다.
- 기업이나 연구기관의 발표가 실제 진보인지 홍보성 주장인지 구분하기 어렵다.
- 특정 기술이 연구 단계인지, 프로토타입 단계인지, 상용화 단계인지 한눈에 보기 어렵다.
- 분야별 최신 흐름을 보려면 많은 자료를 직접 읽어야 한다.
- 커뮤니티의 관심도와 실제 검증 수준이 섞여 잘못 이해되기 쉽다.

TechGraph의 목표는 특정 기술을 검색했을 때, 사용자가 3분 안에 다음을 이해할 수 있게 하는 것이다.

- 현재 기술 수준
- 주요 근거
- 발표 주체
- 검증 상태
- 남은 병목
- 이전 대비 무엇이 진보했는지

## 3. 서비스의 핵심 원칙

TechGraph는 일반 뉴스 커뮤니티가 아니라, 기술 진보를 정리하는 지식 지도에 가깝다.

핵심 원칙은 다음과 같다.

- 누구나 증거를 제보할 수 있다.
- 하지만 기술 지도에 반영되는 내용은 검토를 거친다.
- 좋아요, 조회수, 댓글 수는 관심도일 뿐 검증 상태가 아니다.
- 출처 없는 주장은 기술 진보로 반영하지 않는다.
- 기업 발표는 주장으로 취급하고, 독립 검증과 구분한다.
- 논문도 peer review 여부, 재현 여부, 실험 조건을 구분한다.
- 분야 확장은 제한적으로 관리한다.
- 관리자나 검토자의 판단은 기록으로 남긴다.

## 4. 핵심 사용자

### 연구자

자기 분야의 최신 진보, 경쟁 연구, 재현 여부를 확인한다.

### 엔지니어와 제품 기획자

특정 기술이 실제 제품이나 시스템에 적용 가능한 수준인지 확인한다.

### 창업자와 투자자

기술이 과장된 주장인지, 상용화 가능한 단계인지 판단한다.

### 기자와 애널리스트

기술 발표의 신뢰도, 맥락, 이전 대비 변화량을 확인한다.

### 과학기술 관심 사용자

AI, 로봇, 배터리, 핵융합, 양자컴퓨팅 같은 분야가 실제로 어디까지 발전했는지 이해한다.

## 5. 정보 구조

TechGraph의 정보 구조는 다음처럼 잡는다.

```text
대분류
  중분류
    세부 기술
      주장
      증거
      검증
      타임라인
      성숙도
```

예시:

```text
에너지
  배터리
    전고체 배터리
    리튬메탈 배터리
    나트륨이온 배터리

인공지능
  생성 모델
    대규모 언어모델
    영상 생성 모델
    멀티모달 모델

로봇
  휴머노이드
  로봇 제어
  산업 자동화
```

## 6. 게시물의 기본 단위: 주장과 증거

사용자가 올리는 기본 단위는 단순한 자유게시물이 아니라 `주장`이다.

예시:

```text
주장:
ABC 회사가 전고체 배터리 셀에서 500Wh/kg 에너지 밀도를 달성했다고 발표했다.

출처:
회사 보도자료, 발표 영상, 기술 문서

한계:
셀 단위 실험이며, 사이클 수명과 양산 수율은 공개되지 않았다.

현재 판단:
의미 있는 연구 진전일 수 있으나 상용화 단계로 보기는 어렵다.
```

주장에는 다음 정보가 필요하다.

- 제목
- 관련 분야
- 관련 세부 기술
- 주장 요약
- 출처 링크
- 출처 유형
- 진보 유형
- 이전 상태 대비 변화
- 한계 또는 불확실성
- 제출자 의견
- 검증 상태

## 7. 출처 유형

출처는 유형별로 구분해야 한다.

- 논문
- preprint
- peer-reviewed 논문
- 기업 발표
- 제품 출시
- 특허
- 정부 또는 규제기관 문서
- 독립 실험
- 벤치마크
- 학회 발표
- 데이터셋 또는 코드 공개
- 언론 보도

언론 보도는 보조 출처로 취급하고, 원문 출처를 우선한다.

## 8. 진보 유형

기술이 진보했다는 주장은 무엇이 나아졌는지 분류되어야 한다.

- 성능 향상
- 비용 감소
- 효율 향상
- 안정성 향상
- 수명 증가
- 소형화
- 대량 생산 가능성 증가
- 재현 성공
- 실제 제품 적용
- 규제 승인
- 인프라 구축
- 새로운 이론 또는 방법 제안

## 9. 기술 성숙도 단계

기술 성숙도는 단순한 점수보다 단계형으로 관리하는 것이 좋다.

초기 기준은 다음과 같이 둔다.

```text
1. 이론 제안
2. 실험실 검증
3. 논문 또는 공개 발표
4. 독립 재현
5. 프로토타입
6. 제한적 실사용
7. 제한적 상용화
8. 대규모 상용화
9. 사회 인프라화
```

중요한 점은 성숙도 변경을 일반 게시물과 분리하는 것이다. 사용자는 증거를 제보할 수 있지만, 성숙도 변경은 검토 후 반영되어야 한다.

## 10. 게시물 상태

각 주장은 검토 상태를 가진다.

```text
미검토
출처 확인됨
중복
의미 있는 진보
한계 있음
과장 가능성 있음
논쟁 중
반박됨
타임라인 반영됨
성숙도 반영됨
```

상태는 하나만 붙을 수도 있고, 여러 개가 함께 붙을 수도 있다.

예:

```text
출처 확인됨
한계 있음
논쟁 중
```

## 11. PR 같은 검토 흐름

TechGraph는 모든 게시물을 PR처럼 막아두면 커뮤니티가 성장하기 어렵다. 반대로 모든 게시물을 자유롭게 반영하면 신뢰도가 무너진다.

따라서 두 단계로 나눈다.

### 1단계: 증거 제보

- 누구나 올릴 수 있다.
- 공개는 바로 된다.
- 기본 상태는 `미검토`다.
- 다른 사용자가 댓글, 추가 출처, 반론을 달 수 있다.
- 검토자가 출처와 내용을 확인할 수 있다.

### 2단계: 기술 지도 반영

다음 변경은 PR처럼 승인 과정을 거친다.

- 기술 성숙도 변경
- 타임라인 공식 반영
- 새 세부 기술 생성
- 기존 기술 설명 수정
- 분야 병합 또는 분리
- 현재 최고 수준 수치 변경
- 핵심 병목 업데이트

예시 흐름:

```text
사용자 제보
  -> 미검토 게시물 생성
  -> 출처 확인
  -> 검토자 토론
  -> 분야 관리자 승인
  -> 기술 타임라인 반영
```

성숙도 변경 예시:

```text
제안:
전고체 배터리의 성숙도를 "실험실 검증"에서 "파일럿 생산"으로 변경

필요 근거:
- 파일럿 라인 존재 여부
- 생산 규모
- 셀 성능 데이터
- 사이클 수명
- 독립 확인 자료
- 상용 제품 여부
```

## 12. 역할과 권한

초기에는 역할을 너무 복잡하게 만들지 않는다.

### 일반 사용자

- 증거 제보
- 댓글 작성
- 출처 추가
- 오류 지적
- 새 기술 제안

### 검증 사용자

- 출처 확인
- 중복 표시
- 한계 표시
- 과장 가능성 표시
- 반박 자료 연결
- 신뢰도 평가

### 분야 관리자

- 기술 타임라인 반영 승인
- 성숙도 변경 승인
- 세부 기술 생성 승인
- 중복 기술 병합
- 분야 설명 관리

### 운영진

- 대분류 관리
- 분야 관리자 임명
- 악성 사용자 제재
- 정책 관리
- 분쟁 조정

## 13. 분야 확장 정책

기술 분야는 무한정 늘어나면 안 된다. 분야 구조가 흐트러지면 서비스의 가치가 떨어진다.

추천 정책:

```text
대분류: 운영진만 생성
중분류: 운영진 또는 분야 관리자 승인 필요
세부 기술: 사용자 제안 가능, 승인 후 생성
태그: 비교적 자유롭게 사용 가능
```

사용자는 새 분야를 바로 만들 수 없고, `새 기술 제안`을 제출한다.

제안에는 다음 정보가 필요하다.

- 기술 이름
- 상위 분야 후보
- 왜 별도 기술로 분리해야 하는지
- 기존 기술과 다른 점
- 관련 출처 2개 이상

처리 결과는 다음 중 하나다.

- 승인
- 기존 기술에 병합
- 태그로 처리
- 보류
- 반려

## 14. 신뢰도와 평판

사용자의 좋아요 수와 검증 권한은 분리해야 한다.

검증 권한은 다음 행동을 바탕으로 점진적으로 부여하는 방식이 좋다.

- 정확한 출처 제보
- 중복 제보 정리
- 반박 자료 제시
- 분야 관리자에게 승인된 수정 제안
- 일정 기간 문제 없는 활동

단, 평판 점수가 높아도 혼자 기술 성숙도를 바꿀 수는 없어야 한다. 중요한 변경은 최소 1명 이상의 분야 관리자 승인을 거친다.

## 17. UI/UX 방향

TechGraph의 UI는 단순 게시판이 아니라, 기술별 현재 상태를 보여주는 지도 위에 커뮤니티가 증거를 계속 붙여가는 구조여야 한다.

핵심 방향은 다음과 같다.

```text
Reddit처럼 올리기 쉽다.
GitHub처럼 변경 이력이 남는다.
Wikipedia처럼 정리된 지식 페이지가 있다.
논문 리뷰처럼 근거와 한계가 보인다.
```

사용자가 첫 화면에서 받아야 하는 인상은 "사람들이 떠드는 곳"이 아니라 "기술이 실제로 어디까지 왔는지 확인하는 곳"이다.

## 18. UI 핵심 원칙

### 게시판보다 기술 상황판

홈 화면은 일반 커뮤니티 피드보다 기술 상황판에 가까워야 한다.

추천 구성:

```text
상단: 검색
중앙: 분야별 기술 진보 현황
오른쪽: 검토 대기, 논쟁 중, 최근 반영
아래: 최근 제보된 증거
```

중요한 것은 글 목록을 먼저 보여주는 것이 아니라, 분야별 변화와 검증 상태를 먼저 보여주는 것이다.

### 관심도와 검증을 분리

좋아요, 조회수, 댓글 수는 관심도다. 검증 상태와 섞으면 안 된다.

대신 커뮤니티 액션은 서비스 품질에 직접 연결되게 만든다.

예시:

```text
출처 도움됨
반론 타당함
중복 가능
검증 필요
타임라인 반영 후보
과장 가능성 있음
```

이런 액션은 단순 인기 투표보다 유용하다. 사용자의 행동이 자료 정리, 검증, 반론, 중복 제거에 연결되기 때문이다.

### 기술 페이지를 중심에 둔다

TechGraph의 중심 화면은 게시물 상세가 아니라 기술 상세 페이지다.

예를 들어 `전고체 배터리` 페이지는 다음 정보를 한 화면에서 보여줘야 한다.

```text
전고체 배터리

현재 단계: 프로토타입 / 제한적 파일럿 생산
신뢰도: 중간
최근 변화: Toyota, QuantumScape, Samsung SDI 관련 발표 반영
핵심 병목: 수명, 계면 저항, 양산 수율, 비용

타임라인:
2021 - 실험실 셀 성능 개선
2023 - 파일럿 라인 발표
2025 - 샘플 공급 발표
2026 - 상용화 일정 논쟁 중

최근 주장:
- A 회사가 500Wh/kg 셀 발표
- B 논문이 1000회 사이클 달성 주장
- C 기업의 양산 일정 지연
```

기술 상세 페이지는 해당 기술의 현재 상태를 요약하는 지식 페이지여야 한다. 관련 게시물은 그 상태를 뒷받침하는 근거로 배치한다.

### 주장 상세는 판단 구조를 먼저 보여준다

주장 상세 페이지는 댓글보다 판단 구조가 먼저 보여야 한다.

추천 구성:

```text
[상태 배지] 출처 확인됨 / 한계 있음 / 논쟁 중

주장:
ABC 회사가 전고체 배터리 500Wh/kg을 달성했다고 발표했다.

현재 판단:
의미 있는 진전일 가능성은 있으나, 셀 단위 실험이고 수명 데이터가 부족하다.

출처:
- 회사 보도자료
- 발표 영상
- 기술 문서

검토:
- 출처 확인됨
- 독립 재현 없음
- 양산성 불명확

댓글:
토론, 반론, 추가 자료
```

댓글은 중요하지만 화면의 중심이 되면 안 된다. 중심은 주장, 근거, 검증 상태, 한계다.

## 19. 주요 화면별 UI 설계

### 홈

홈은 최신 글 목록이 아니라 기술 진보 대시보드다.

필수 요소:

- 전체 검색
- 주요 분야 카드
- 최근 검증된 기술 진보
- 논쟁 중인 주장
- 타임라인에 최근 반영된 항목
- 검토 대기 중인 주요 제보
- 상용화 임박 기술

홈에서 보여줄 분야 카드는 단순 카테고리 링크가 아니라, 분야 상태 요약이어야 한다.

예시:

```text
배터리
최근 변화: 전고체 배터리 파일럿 생산 주장 2건 검토 중
논쟁 중: 500Wh/kg 셀 발표의 재현 가능성
성숙도 변화: 없음
```

### 기술 상세 페이지

기술 상세 페이지는 가장 중요한 화면이다.

필수 요소:

- 기술 이름
- 현재 성숙도
- 현재 상태 요약
- 신뢰도 또는 검증 수준
- 최근 주요 변화
- 핵심 병목
- 타임라인
- 주요 조직
- 관련 주장
- 관련 논문, 제품, 특허, 발표
- 성숙도 변경 제안 버튼
- 새 증거 제보 버튼

이 화면은 반복 방문자가 빠르게 변화를 파악할 수 있게 만들어야 한다.

### 주장 상세 페이지

주장 상세 페이지는 하나의 기술 진보 주장에 대한 검토 화면이다.

필수 요소:

- 상태 배지
- 주장 요약
- 출처
- 출처 유형
- 진보 유형
- 이전 상태 대비 변화
- 현재 판단
- 한계와 불확실성
- 반론
- 추가 출처
- 관련 기술
- 타임라인 반영 여부
- 댓글

중요한 액션:

- 출처 확인
- 추가 출처 제안
- 반론 제기
- 중복 신고
- 검증 요청
- 타임라인 반영 제안
- 성숙도 변경 제안

### 증거 제보 페이지

증거 제보 페이지는 일반 글쓰기보다 구조화되어야 한다.

필수 입력:

- 제목
- 출처 URL
- 관련 분야
- 관련 세부 기술
- 주장 요약
- 무엇이 진보했는지
- 이전 상태와 비교했을 때 달라진 점
- 한계 또는 불확실성
- 출처 유형
- 진보 유형

입력 화면은 사용자가 자연스럽게 근거 중심으로 쓰도록 유도해야 한다.

나쁜 입력:

```text
이 회사 기술 미쳤음
```

좋은 입력:

```text
ABC 회사가 500Wh/kg 배터리 셀을 발표했다.
다만 셀 단위 실험이며, 사이클 수명과 양산 수율은 공개되지 않았다.
```

### 새 기술 제안 페이지

새 기술은 자유롭게 생성하지 않고 제안 후 승인한다.

필수 입력:

- 기술 이름
- 상위 분야 후보
- 기존 기술과 다른 점
- 별도 항목으로 필요한 이유
- 관련 출처 2개 이상
- 병합 가능한 기존 기술

결과 상태:

- 승인
- 기존 기술에 병합
- 태그로 처리
- 보류
- 반려

### 관리자/검토자 화면

MVP에서도 관리자/검토자 화면은 필요하다. 이 서비스는 검토 구조가 핵심이기 때문이다.

필수 요소:

- 검토 대기 주장
- 새 기술 제안
- 성숙도 변경 제안
- 타임라인 반영 제안
- 논쟁 중인 주장
- 신고된 게시물
- 중복 후보
- 최근 관리자 판단 이력

관리자 판단에는 반드시 이유가 남아야 한다.

예시:

```text
반려 사유:
출처가 언론 보도뿐이며 원문 발표 자료가 없음.

보류 사유:
기업 발표는 확인됐지만 성능 수치의 실험 조건이 공개되지 않음.

승인 사유:
논문, 코드, 독립 재현 자료가 모두 확인됨.
```

## 20. 시각 디자인 방향

디자인 톤은 다음에 가깝게 잡는다.

```text
기술 정보 플랫폼
리서치 대시보드
개발자 커뮤니티
위키형 지식베이스
```

피해야 할 톤:

```text
뉴스 포털
자극적인 커뮤니티
트위터식 피드
디시/레딧 복제
블로그 모음집
```

색상은 중립적인 정보 플랫폼 톤을 기본으로 하되, 상태 색은 명확하게 쓴다.

예시:

```text
검증됨: 녹색
논쟁 중: 노란색
반박됨: 빨간색
미검토: 회색
타임라인 반영: 파란색
과장 가능성: 주황색
```

상태 배지는 매우 중요하다. 사용자는 글 제목보다 먼저 검증 상태를 이해할 수 있어야 한다.

## 21. MVP UI 우선순위

처음부터 완전한 커뮤니티를 만들기보다 다음 순서로 구축한다.

1. 기술 목록 화면
2. 기술 상세 화면
3. 주장 상세 화면
4. 증거 제보 화면
5. 검토 상태 표시
6. 댓글과 반론
7. 새 기술 제안
8. 관리자 검토 화면

초기 UI의 성공 기준은 다음과 같다.

- 사용자가 특정 기술의 현재 상태를 빠르게 이해할 수 있다.
- 어떤 주장이 검증됐고 어떤 주장이 논쟁 중인지 명확하다.
- 출처와 한계가 제목보다 약하게 숨겨지지 않는다.
- 사용자가 글을 쓸 때 자연스럽게 근거와 한계를 함께 제출한다.
- 관리자가 기술 지도에 반영할 항목을 빠르게 검토할 수 있다.

## 22. 운영 방식 요약

TechGraph는 다음 구조로 운영하는 것이 좋다.

```text
자유롭게 제보한다.
검토 상태를 분명히 표시한다.
기술 지도 반영은 승인제로 한다.
분야 확장은 제한한다.
관리 판단은 기록한다.
좋아요와 검증을 분리한다.
```

즉, GitHub PR, Reddit식 자발적 관리자, 위키식 편집 승인 구조를 섞되, 과학기술 분야에 맞게 증거와 검증을 중심에 둔다.

## 23. 다음에 결정할 것

다음 논의에서 정해야 할 것들:

- 첫 MVP에서 다룰 기술 분야를 3개로 줄일지, 5개로 시작할지
- 게시물을 처음부터 공개할지, 스팸 방지를 위해 임시 대기 상태를 둘지
- 검토자는 운영진만 둘지, 초기 신뢰 사용자도 둘지
- 기술 성숙도 단계를 9단계로 할지, 더 단순한 5단계로 할지
- 한국어 중심 서비스로 시작할지, 영어 자료 기반 글로벌 서비스로 갈지
- 일반 커뮤니티 기능을 어느 정도까지 열어둘지
- 기술 지도의 최종 수정 권한을 누가 가질지
- 홈을 커뮤니티 피드 중심으로 둘지, 기술 상황판 중심으로 둘지
- 모바일에서 기술 상세 페이지의 우선순위를 어떻게 둘지
- 관리자/검토자 화면을 MVP에 포함할지
